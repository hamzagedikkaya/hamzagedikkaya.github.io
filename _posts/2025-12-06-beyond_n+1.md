Every Rails developer learns the N+1 lesson early: loop over `posts`, call `post.author` inside the loop, watch the log fill with identical `SELECT * FROM users WHERE id = ?` lines. Then they install [Bullet](https://github.com/flyerhzm/bullet), it starts shouting about missing `includes`, and the problem feels solved.

It isn't. Bullet is excellent at the one thing it does — noticing an association that wasn't preloaded — but a large share of the query storms I've debugged in production never showed up in Bullet's output at all. They hid inside custom methods, serializers, callbacks, and the wrong choice between `count` and `size`. This post is a field guide to those traps: how to recognize each one, why Bullet is blind to it, and what to do instead.

> *Updated September 2026* with a section on `strict_loading`, a detection cheat sheet, and pointers to the static analyzer this post eventually led me to build.

## 1. What Bullet Sees — and What It Doesn't

Bullet hooks into ActiveRecord's **association loading**. When you call `user.teams`, it checks whether that association was preloaded on the parent collection and complains if it wasn't. That's the whole mechanism, and it explains every blind spot:

- **Queries inside custom methods** — `teams.where(...)`, `.exists?`, `.find_by` build a *new* relation and never touch the association cache.
- **Serializers** — attribute blocks that reach into associations run once per record, outside anything Bullet instruments.
- **Callbacks** — queries in `after_save` and friends, which are also where bulk operations hurt most.
- **Code your tests don't execute** — Bullet is a runtime tool; an untested admin export is invisible to it.
- **Tiny fixtures** — a test with 2 records may never trigger the threshold that 10,000 production rows would.
- **Background jobs** — no request cycle, so no Bullet report unless you wire it up manually.

Here's the canonical example Bullet stays quiet on:

```ruby
class User < ApplicationRecord
  has_many :teams

  def supports?(team_name)
    teams.where(name: team_name).exists?
  end
end
```

```erb
<% @users.each do |user| %>
  <li class="<%= user.supports?("Lakers") ? "purple" : "" %>"><%= user.name %></li>
<% end %>
```

100 users, 101 queries, zero warnings. `teams.where(...)` is a fresh relation; the association was never "loaded", so there's nothing for Bullet to flag.

## 2. Hidden N+1s in Custom Methods

### The problem

```ruby
class Order < ApplicationRecord
  belongs_to :user
  has_many :line_items

  def total_with_discount
    user.loyalty_tier.discount_rate * line_items.sum(:price)   # 3 queries per order
  end
end

# Controller
@orders = Order.includes(:line_items).limit(50)
```

`line_items` is preloaded, so Bullet is happy. But `user` isn't, `loyalty_tier` isn't, and `line_items.sum(:price)` issues a `SUM` query regardless of the preload — `sum` with a column argument always hits the database.

### Fix 1: preload the whole chain

```ruby
@orders = Order.includes(:line_items, user: :loyalty_tier).limit(50)
```

And change `line_items.sum(:price)` to `line_items.sum(&:price)` — the block form iterates the loaded array in Ruby instead of querying.

### Fix 2: compute in bulk, pass the result in

When the method is called from many places and you can't control every caller's preload, move the computation out:

```ruby
def index
  @orders = Order.includes(:line_items).limit(50)
  @discount_rates = User.joins(:loyalty_tier)
                        .where(id: @orders.map(&:user_id))
                        .pluck(:id, "loyalty_tiers.discount_rate")
                        .to_h
end
```

```ruby
def total_with_discount(rate = user.loyalty_tier.discount_rate)
  rate * line_items.sum(&:price)
end
```

### Fix 3: detect it with Prosopite

[Prosopite](https://github.com/charkost/prosopite) takes the opposite approach to Bullet: it doesn't care about associations at all. It fingerprints every SQL statement in a request and raises when the same shape repeats with different bind values. That catches `supports?` and `total_with_discount` on the first run.

```ruby
# Gemfile
gem "prosopite", group: [:development, :test]

# config/environments/development.rb
config.after_initialize do
  Prosopite.rails_logger = true
  Prosopite.raise        = true
end
```

Bullet and Prosopite aren't alternatives — Bullet also flags *unused* eager loading, which Prosopite can't see. Run both.

## 3. Serializer-Induced Query Explosions

Serializers are an N+1 graveyard: they run once per record, they routinely reach two associations deep, and the controller rendering them usually has no idea which fields they touch.

```ruby
class PostSerializer < ActiveModel::Serializer
  attributes :id, :title, :author_name, :comments_count

  def author_name    = object.user.name        # query per post
  def comments_count = object.comments.count   # COUNT per post
end

render json: Post.all   # 1 + 2N queries
```

### Fix 1: preload where you render

```ruby
render json: Post.includes(:user, :comments)
```

Simple, but the coupling is fragile — the next person to add a field to the serializer won't know to update every controller that renders it.

### Fix 2: make the serializer refuse to lazy-load

```ruby
def author_name
  return unless object.association(:user).loaded?
  object.user.name
end
```

The field goes missing in development the moment someone forgets the preload, which is loud enough to get fixed. Combine with `strict_loading` (§7) for an exception instead of a nil.

### Fix 3: batch at the boundary

For GraphQL-shaped or deeply nested APIs, [batch-loader](https://github.com/exAspArk/batch-loader) collects IDs during serialization and resolves them in one query at the end:

```ruby
def author
  BatchLoader.for(object.user_id).batch do |user_ids, loader|
    User.where(id: user_ids).each { |u| loader.call(u.id, u) }
  end
end
```

### Fix 4: counter caches for counts

`comments_count` should almost never be a live `COUNT`. See §4.

## 4. The count / size / length Trap

Three methods, identical results, wildly different behaviour:

| Method | If the association is loaded | If it isn't |
|---|---|---|
| `count` | **Runs `SELECT COUNT(*)` anyway** | `SELECT COUNT(*)` |
| `size` | Ruby `Array#size` — no query | `SELECT COUNT(*)` |
| `length` | Ruby `Array#length` — no query | **Loads every record**, then counts |

```ruby
@users = User.includes(:posts)

@users.each { |u| u.posts.count }   # N COUNT queries despite the preload
@users.each { |u| u.posts.size }    # 0 extra queries
```

This is the trap Bullet *cannot* see by definition: the association **was** preloaded, so nothing is wrong from its point of view. You just aren't using the preload.

`size` is the right default in almost every case. Reach for `count` only when you specifically want a fresh number and don't care about the loaded array; reach for `length` never.

### When counts are hot: counter caches

If a count is displayed on every list row, don't compute it at all — store it:

```ruby
# migration
add_column :users, :posts_count, :integer, default: 0, null: false

# app/models/post.rb
belongs_to :user, counter_cache: true

# one-time backfill
User.in_batches.each_record { |u| User.reset_counters(u.id, :posts) }
```

For conditional counts (only *published* posts, only *cancelled* orders) the built-in counter cache isn't enough; [counter_culture](https://github.com/magnusvk/counter_culture) handles those:

```ruby
counter_culture :customer,
  column_name: ->(order) { order.cancelled? ? "cancelled_orders_count" : nil }
```

## 5. Silent Killers in Callbacks

A callback that runs one query is harmless on a form submit and catastrophic in an import.

```ruby
class Article < ApplicationRecord
  after_save :update_search_index    # external HTTP call
  after_save :notify_subscribers     # N mail jobs, N queries
  after_save :recalculate_stats      # COUNT + UPDATE

  private

  def notify_subscribers
    subscribers.each { |s| NotificationMailer.new_article(s, self).deliver_later }
  end

  def recalculate_stats
    author.articles.published.count
    category.update_article_count!
  end
end

articles_data.each { |attrs| Article.create!(attrs) }   # 1,000 articles → thousands of side effects
```

### Fix 1: `insert_all` / `upsert_all` for bulk writes

```ruby
Article.insert_all(articles_data)   # one INSERT, no callbacks, no validations
```

Then run the side effects once, in bulk, from a job. The trade-off is explicit: you own uniqueness and validation at the database level (unique indexes, `NOT NULL`, check constraints).

### Fix 2: `after_commit` + a job

```ruby
after_commit :schedule_notifications, on: :create

def schedule_notifications
  NotifySubscribersJob.perform_later(id)
end
```

`after_commit` also fixes a subtler bug: with `after_save`, the job can run before the transaction commits and fail to find the record.

### Fix 3: a transaction-scoped bypass flag

```ruby
attr_accessor :skip_side_effects

after_save :notify_subscribers, unless: :skip_side_effects
```

Useful for imports that still need validations. Just make sure the flag is set at the call site and never persists.

### Fix 4: `suppress` for a specific model

```ruby
Notification.suppress do
  Article.create!(attrs)   # any Notification.create inside the block is a no-op
end
```

`ActiveRecord::Suppressor` silences *saves of one model class* within the block — handy for "don't create notifications during this migration", not a general callback switch.

## 6. select vs pluck: Memory and Speed

```ruby
User.all.map(&:id)          # loads every column, instantiates every object
User.select(:id).map(&:id)  # one column, but still N ActiveRecord objects
User.pluck(:id)             # one column, plain Ruby array
```

On 10,000 rows, on my machine, the three run in roughly 270 ms, 100 ms, and 15 ms. The order never changes; only the ratios do.

### Rules of thumb

```ruby
# pluck when you want values
emails = User.where(role: :admin).pluck(:email)

# select when you need model methods on the result
User.select(:id, :name, :email).each { |u| u.display_name }

# select (not pluck) inside a where — it becomes a subquery
Post.where(user_id: User.active.select(:id))
#   SELECT posts.* WHERE user_id IN (SELECT id FROM users WHERE active)

# pluck inside a where — two round trips and an array in memory
Post.where(user_id: User.active.pluck(:id))
```

The last one is the most common mistake. `pluck` executes immediately; `select` stays lazy and lets PostgreSQL do the join.

### Large datasets

```ruby
User.select(:id, :email).find_each(batch_size: 1_000) { |u| process(u) }   # bounded memory
User.in_batches(of: 5_000).update_all(flagged: true)                       # bulk without instantiation
```

## 7. strict_loading: Making Rails Refuse to Lazy-Load

Rails 6.1 added the tool this post has been circling around: a mode where lazy-loading an association **raises** instead of quietly firing a query.

```ruby
# on a relation
posts = Post.strict_loading.includes(:author)
posts.first.comments   # ActiveRecord::StrictLoadingViolationError

# on a single record
user = User.strict_loading.find(id)

# on an association definition
has_many :comments, strict_loading: true

# on a whole model
class Post < ApplicationRecord
  self.strict_loading_by_default = true
end
```

The most useful setting is global, for development and test only:

```ruby
# config/environments/development.rb, config/environments/test.rb
config.active_record.strict_loading_by_default = true
config.active_record.action_on_strict_loading_violation = :log   # :raise once you've cleaned up
```

Start with `:log` — an existing app will produce a wall of violations. Fix them in order of how hot the path is, then switch to `:raise` so new violations fail the test suite.

Why this matters more than Bullet: `strict_loading` is enforced *by ActiveRecord itself*, so it fires on the serializer field, the custom method, the callback, the job — anywhere a lazy load happens. What it still can't do is see code paths that never run in tests, which is where §10 and static analysis come in.

## 8. Finding the Real Bottleneck with EXPLAIN ANALYZE

Sometimes there's no N+1 at all — just one slow query. `EXPLAIN ANALYZE` executes the statement and shows what PostgreSQL actually did.

```ruby
User.where(email: "test@example.com").explain            # plan only
User.where(email: "test@example.com").explain(:analyze)  # runs the query, real timings (Rails 7.1+)
```

```text
-- Bad: sequential scan, 99,999 rows read to find 1
Seq Scan on users  (cost=0.00..1234.00 rows=1 width=244) (actual time=45.1..89.4 rows=1 loops=1)
  Filter: (email = 'test@example.com')
  Rows Removed by Filter: 99999

-- Good: index scan
Index Scan using index_users_on_email on users  (cost=0.42..8.44 rows=1 width=244) (actual time=0.026..0.027 rows=1 loops=1)
  Index Cond: (email = 'test@example.com')
```

### Red flags

| In the plan | Means | Try |
|---|---|---|
| `Seq Scan` on a large table | no usable index | add one, or fix the predicate so the existing one applies |
| high `Rows Removed by Filter` | the index narrows too little | composite or partial index |
| `Sort` with high cost, `external merge` | sorting on disk | index that matches `ORDER BY`, raise `work_mem` |
| `Nested Loop` with `loops=` in the thousands | join without an index on the inner side | index the foreign key |
| `rows=` estimate far from `actual rows` | stale statistics | `ANALYZE table` |

### Instance-wide view

[PgHero](https://github.com/ankane/pghero) and [rails-pg-extras](https://github.com/pawurb/rails-pg-extras) answer the questions a single `EXPLAIN` can't: which queries dominate total time, which indexes are never used, what the cache hit rate is.

```ruby
PgHero.slow_queries
RailsPgExtras.unused_indexes
RailsPgExtras.cache_hit        # index hit rate under ~99% deserves a look
```

## 9. Index Strategies That Actually Get Used

### Composite indexes: column order is everything

```ruby
add_index :orders, [:user_id, :status, :created_at]
```

PostgreSQL uses a B-tree left to right. These use it:

```ruby
Order.where(user_id: 1)
Order.where(user_id: 1, status: "pending")
Order.where(user_id: 1, status: "pending").order(created_at: :desc)
```

This doesn't — `user_id` is skipped, so the index prefix is gone:

```ruby
Order.where(status: "pending")
```

Put equality columns first, the range or sort column last.

### Partial indexes

Index only the rows you query:

```ruby
add_index :users, :email, where: "deleted_at IS NULL", name: "index_active_users_on_email"
add_index :orders, :created_at, where: "status = 'pending'", name: "index_pending_orders_on_created_at"
```

Smaller index, faster writes, and often the only way to make a low-cardinality `status` column worth indexing.

### Covering indexes

If every column the query needs is in the index, PostgreSQL never touches the table:

```ruby
add_index :users, :email, include: [:name, :role]   # Rails 7.1+ syntax for INCLUDE
User.where(email: "x@y.com").select(:name, :role)   # Index Only Scan
```

### Expression indexes

The index must match the expression *exactly*:

```ruby
add_index :users, "LOWER(email)", name: "index_users_on_lower_email"
User.where("LOWER(email) = ?", email.downcase)
```

### GIN for JSONB, arrays, and full-text

```ruby
add_index :products, :metadata, using: :gin
add_index :articles, :tags,     using: :gin
add_index :articles, "to_tsvector('english', title || ' ' || content)", using: :gin, name: "index_articles_fts"
```

## 10. Tooling, Tests, and Production Monitoring

### Development

```ruby
group :development do
  gem "bullet"                 # unpreloaded and *unused* eager loading
  gem "prosopite"              # repeated-query fingerprinting
  gem "rack-mini-profiler"     # per-request SQL and timing badge
  gem "memory_profiler"
  gem "rails-pg-extras"
end
```

### Tests that fail on regressions

[n_plus_one_control](https://github.com/palkan/n_plus_one_control) asserts that query count doesn't scale with record count:

```ruby
require "n_plus_one_control/rspec"

RSpec.describe "GET /users", type: :request do
  populate { |n| create_list(:user, n, :with_posts) }

  it "runs a constant number of queries" do
    expect { get "/users" }.to perform_constant_number_of_queries
  end
end
```

Pair it with `strict_loading_by_default` in the test environment so lazy loads raise.

### CI

```ruby
# spec/rails_helper.rb
if ENV["CI"]
  Bullet.enable = true
  Bullet.raise  = true
end
```

### Production

```ruby
# config/initializers/slow_query_logger.rb
ActiveSupport::Notifications.subscribe("sql.active_record") do |*, payload|
  next if payload[:name] == "SCHEMA" || payload[:duration] < 100

  Rails.logger.warn("[SLOW SQL] #{payload[:duration].round(1)}ms #{payload[:sql].squish}")
end
```

An APM (Skylight, Scout, AppSignal, New Relic) is worth it purely for the per-endpoint "N queries of the same shape" view, which is the production equivalent of Prosopite.

## 11. Detection Cheat Sheet

| Trap | Bullet | Prosopite | strict_loading | Static analysis |
|---|:-:|:-:|:-:|:-:|
| Missing `includes` in a loop | ✅ | ✅ | ✅ | ✅ |
| Query inside a custom method | ❌ | ✅ | ✅ | ✅ |
| Serializer reaching into associations | ❌ | ✅ | ✅ | ✅ |
| `.count` on a preloaded association | ❌ | ✅ | ❌ | ✅ |
| Queries in callbacks during bulk writes | ❌ | ✅ | partial | ✅ |
| `pluck` inside `where` | ❌ | ❌ | ❌ | ✅ |
| Code paths tests never run | ❌ | ❌ | ❌ | ✅ |
| Unused eager loading | ✅ | ❌ | ❌ | ❌ |
| Slow single query / missing index | ❌ | ❌ | ❌ | ❌ → `EXPLAIN`, PgHero |

The last column is the gap this post left open when it was first published: everything above can be found by *reading the code*, without running it. I eventually built exactly that — a static analyzer that parses your Ruby into an AST and flags these patterns in CI, with no database, no fixtures, and no Rails boot. It's called [EagerEye]({% post_url 2026-05-03-eager_eye_static_analysis %}), and the follow-up post covers its design and the numbers from running it on two production codebases.

## Conclusion

Bullet tracks *association loading*, not *query execution*. Every code path that produces queries without going through the association cache — custom methods, serializers, callbacks, `count` on a loaded collection — is invisible to it.

The practical stack in 2026:

1. **`strict_loading_by_default`** in development and test, so lazy loads are loud
2. **Bullet + Prosopite** together — they have complementary blind spots
3. **`size` over `count`**, counter caches for anything displayed in a list
4. **`insert_all` / `after_commit` + jobs** so callbacks can't multiply
5. **`EXPLAIN ANALYZE`** before adding an index, PgHero to find the indexes you never use
6. **Static analysis in CI** for the code your tests don't reach
