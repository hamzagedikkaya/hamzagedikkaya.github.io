For the last few years, the parts of my life that I actually wanted to track had drifted into six different apps. One for money. One for habits. Another for todos. A separate calendar. A journal app that, of course, lived in yet another silo. Each one a tiny monthly fee. Each one a tiny export format that didn't talk to anyone else. Each one a tiny promise that *your data is yours* — quietly disproved the moment you tried to leave.

[Meridian](https://github.com/hamzagedikkaya/meridian) is what I built to stop renting my own life. It's a single Rails 8 application — finance, habits, todos, calendar, journal, goals, insights — that runs on a machine I control, dumps its entire state into one `tar.gz` when I want a backup, and never phones home. No accounts on someone else's server. No "premium tier." No sync that mysteriously breaks the week before tax season.

This post is about the design of that app: what's actually in it, why I chose local-first over a hosted SaaS, the small technical decisions that made it pleasant to live in, and the things I deliberately left out.

## 1. The Problem with Renting Your Own Data

The honest framing isn't "subscriptions are bad." Some of them are excellent products built by people I respect. The problem is structural: each one captures a thin slice of your life, and the slices never connect.

Your finance app knows you spent ₺840 on coffee in March. Your habit app knows your "no caffeine" streak broke on the 14th. Your journal app — if you happen to keep one — knows you wrote *"didn't sleep well, anxious about the demo"* that same morning. Each fact is in someone else's database. Asking the obvious question — *"do my caffeine relapses correlate with my anxious days?"* — is impossible, because no single system has both facts.

It gets worse when you try to leave. CSV exports drop fields. APIs get rate-limited. A pricing change can ransom three years of journal entries behind a tier you didn't sign up for. The data isn't really yours; you're renting access to it.

The local-first answer is the obvious one: **put everything in one Postgres database on a machine you own.** That's the entire thesis behind Meridian. The rest is execution.

## 2. What Meridian Actually Is

Meridian is a single Rails 8 application — not a microservice mesh, not an Electron wrapper around a web view, not a "platform." One repo, one database, one process tree, one backup file.

![Meridian dashboard](/assets/images/posts/meridian_dashboard.png)

The dashboard is a bento grid: today's habits, upcoming todos, today's events, a finance sparkline, goals progress, a journal CTA. It's not designed to look impressive in a screenshot; it's designed to be the first thing I see when I open my laptop in the morning and the last thing I close at night.

The whole stack:

| Layer | Choice |
|---|---|
| Backend | Ruby 3.3, Rails 8 |
| Frontend | Hotwire (Turbo + Stimulus), Importmap, Tailwind v4 |
| UI components | ViewComponent + Lookbook |
| Database | PostgreSQL 14+ |
| Auth | Devise |
| Charts | Chartkick + Chart.js + groupdate |
| Money | money-rails |
| Recurring rules | ice_cube |
| Backup | `pg_dump` + `tar.gz` + ActiveStorage |
| Testing | RSpec, FactoryBot, Capybara, SimpleCov |
| Security | Brakeman + RuboCop omakase |

The mantra was *fewer moving parts, fewer footguns*. No Node.js build server. No Redis (Solid Queue / Solid Cache / Solid Cable handle the background jobs, cache, and ActionCable on Postgres). No third-party fonts loaded from a CDN at runtime. The app boots, serves traffic, and stays alive on a small box without needing babysitting.

## 3. One App, Eight Modules

Each module is its own controller surface and view tree, but they all share the same Postgres database, the same `User`, and the same polymorphic `Tag`/`Tagging` model — so a tag like `work-trip` can sit on a transaction, a todo, a journal entry, and an event simultaneously.

- **Finance** — Accounts, categories, transactions (income / expense / transfer), subscriptions with recurring rules, 6-month trend charts, CSV export. Amounts are stored as `cents` integers via `money-rails`, with a per-account currency.
- **Todos** — Lists, priorities, statuses, due dates, and tab filters (Open / Today / This week / Overdue / Done).
- **Habits** — Daily / weekly / monthly cadences, streak calculation, a 12-week heatmap, completion rate. (More on the streak math in §7.)
- **Calendar** — Monthly grid plus a drag-to-reschedule weekly view, with an iCal feed at `/calendar/feed` so the same data shows up in Apple Calendar or Fantastical.
- **Journal** — ActionText rich body, mood emoji, energy level, gratitude, tags, timeline view.
- **Goals** — Financial / habit / custom targets. Progress is recalculated against live data, not stored as a static number that drifts.
- **Insights** — Cross-module analytics. The whole reason a single database exists.
- **Weekly review** — A guided form that surfaces the past week's stats (todos completed, habit completion, top categories) alongside three reflection prompts.

Bolted onto all of this:

- **Global search** (`⌘K` / `Ctrl+K` / `/`) — Postgres full-text search across every module with arrow-key navigation in the modal.
- **Quick capture** (`c`) — One text input. Smart router. (See §5.)
- **Focus timer** — Pomodoro Stimulus controller with browser notifications and per-todo time tracking.
- **Light / dark** — System / dark / light, persisted to localStorage. Dark-first amber palette by default.
- **Vim-style nav** — `g d`, `g f`, `g t`, `g h`, `g c`, `g j`, `g g` for the major sections.

## 4. The Technical Bones

Choosing Rails 8 wasn't nostalgia. Rails 8 ships with the *Solid* suite — Solid Queue for background jobs, Solid Cache for caching, Solid Cable for ActionCable — all backed by Postgres. That's three subsystems I would have otherwise needed Redis for, gone. The deployment story for a self-hoster collapses to *Postgres + the Rails process*.

The frontend is Hotwire. The architecture follows a principle I've come to believe in more strongly with every project: **render HTML on the server, swap fragments on the client, write Stimulus controllers only for the genuinely interactive bits.** The Pomodoro timer is a Stimulus controller. The drag-to-reschedule weekly calendar is a Stimulus controller. The rest is Turbo Frames and Turbo Streams.

ViewComponent + Lookbook handles the UI primitives. Lookbook is mounted at `/lookbook` in dev only, which means I can preview a `Card`, `Button`, `StatNumber`, or chart component in isolation without spinning up real data. It's a quiet productivity multiplier.

The design tokens live in one file — [`app/assets/tailwind/application.css`](https://github.com/hamzagedikkaya/meridian) — declared inside `@theme` for dark mode and `html.light` for the light overrides. Fraunces (variable serif) for display, DM Sans for body, JetBrains Mono for code. A dark-first amber/gold palette because every other self-hosted app on the planet defaults to blue.

## 5. Quick Capture: One Input, Smart Router

The most-used feature in the whole app is one I almost didn't ship. A floating button (and the `c` shortcut) opens a single text input. Whatever you type gets routed to the right module:

```ruby
class QuickCapturesController < ApplicationController
  def create
    text = params[:text].to_s.strip
    redirect_to root_path, alert: t("quick_capture.empty_alert") and return if text.blank?

    case text
    when /^[+\-]?\d+(\.\d+)?/
      # "120 coffee" → expense, "+5000 salary" → income
      acc = current_user.accounts.active.first
      kind = text.start_with?("+") ? "income" : "expense"
      amount = (text.delete("^0-9.\-").to_f.abs * 100).round
      description = text.sub(/^[+\-]?[\d.]+\s*/, "")
      Transaction.create!(user: current_user, account: acc, amount_cents: amount,
                          kind: kind, description: description, date: Date.current)

    when /^habit:\s*(.+)/i
      # "habit: meditation" → toggle today's log
      name = $1.strip
      habit = current_user.habits.active.find { |h| h.name.downcase == name.downcase }
      habit&.log_for(Date.current)&.update!(completed: true, count: 1)

    when /(?:yarın|tomorrow|tuesday|wednesday|thursday|friday|saturday|sunday|monday)/i
      # Looks like a date → propose an event
      redirect_to new_event_path(event: { title: text })

    else
      # Default: it's a todo
      current_user.todos.create!(title: text, priority: "medium", status: "pending")
    end
  end
end
```

It's a flat `case/when` with four arms. There is no NLP. There is no ML model. There is no "AI assistant." It's regex routing, and it covers somewhere around 95% of the things I actually want to capture in two seconds without breaking flow.

`120 coffee` becomes a transaction. `habit: reading` ticks today's reading habit. `Call dentist tuesday` opens an event form pre-filled. `Reply to Mehmet about the demo` becomes a todo. The friction of capture is roughly *one keypress + one sentence*, which is the threshold at which a system stops being "something I should use" and starts being something I just use.

## 6. Backups as a First-Class Feature

If your data lives on one machine, backups aren't a feature — they're the entire premise. Meridian's backup format is intentionally boring:

```
meridian-backup-YYYYMMDD-HHMMSS/
├── metadata.json   ← Meridian version + schema version + timestamp
├── db.dump         ← pg_dump --format=custom
└── storage/        ← ActiveStorage blob tree (avatars, attachments)
```

That whole tree gets tarred and gzipped into one file. You can `scp` it. You can drop it on a USB stick. You can throw it in iCloud Drive. It is a single file that contains a complete snapshot of *your Meridian*.

Restoring is the inverse: drop the archive into `/backups`, the app extracts it, calls `pg_restore --clean --if-exists`, swaps the ActiveStorage tree, and signs you out so you can sign back in with the restored credentials. There's one important guard:

```ruby
meta = JSON.parse(File.read(File.join(workdir, "metadata.json")))
if meta["schema_version"] && meta["schema_version"] != schema_version
  raise "Schema version mismatch: backup is #{meta['schema_version']} but DB is #{schema_version}"
end
```

The destination database must be on the same migration version as the backup. This trades convenience for safety: you can't accidentally restore a backup taken before a schema-breaking migration into a fresh database with the new schema. Upgrade the destination Meridian to match, then restore.

The whole thing is implemented in [`BackupService`](https://github.com/hamzagedikkaya/meridian) — about 140 lines, including error handling. No external service. No "cloud sync." Just `pg_dump`, `tar`, and a metadata file.

## 7. Habits, Streaks, and Avoiding the N+1 Trap

The habits module looks innocent. Each habit has many `HabitLog` records, one per day. Computing a streak for one habit is easy — pull the completed dates in descending order, walk down until you hit a gap.

The trap is the dashboard, where I render *all* active habits with their current streaks. A naïve `@habits.each(&:current_streak)` triggers one query per habit. With twelve habits that's twelve queries before the heatmap even renders. The fix is a batched calculator:

```ruby
def self.streaks_for(habits)
  habit_ids = habits.map(&:id)
  return {} if habit_ids.empty?

  today = Date.current
  rows = HabitLog.where(habit_id: habit_ids, completed: true, date: ..today)
                 .order(date: :desc).pluck(:habit_id, :date)
  by_habit = rows.group_by(&:first).transform_values { |arr| arr.map(&:last) }

  habit_ids.index_with do |hid|
    dates = by_habit[hid] || []
    cutoff = dates.include?(today) ? today : today - 1.day
    relevant = dates.drop_while { |d| d > cutoff }
    next 0 if relevant.empty? || relevant.first != cutoff

    streak = 1
    relevant.each_cons(2) { |a, b| (a - b).to_i == 1 ? streak += 1 : break }
    streak
  end
end
```

One query, regardless of how many habits you have. This is the kind of decision that doesn't matter on day one but matters every single day after — and it's the kind of N+1 that runtime tools like Bullet sometimes miss, because the loop is inside a custom method instead of a direct association call. (I wrote about that whole class of bug in [Beyond N+1: Hidden Performance Traps and Fixes]({% post_url 2025-12-06-beyond_n+1 %}), and built [EagerEye]({% post_url 2026-05-03-eager_eye_static_analysis %}) to catch it statically. Both are baked into Meridian's `Gemfile`.)

## 8. Insights: The Reason to Have It All in One Database

This is where the local-first thesis pays off. Because finance, habits, journal, todos, and focus sessions all live in the same Postgres database, the insights view can ask questions no individual SaaS app could answer:

```ruby
# Mood × habit completion correlation
entries = current_user.journal_entries.where(date: from..to).where.not(mood: nil)
entries.each do |entry|
  by_mood[entry.mood][:count] += 1
  logs = current_user.habit_logs.where(date: entry.date)
  by_mood[entry.mood][:completed_days] += logs.where(completed: true).count
  by_mood[entry.mood][:total_days]     += logs.count
end
```

That snippet — paired with a chart — answers *"on the days I wrote that I was anxious, what was my habit completion rate?"* Not because some recommendation engine guessed at it. Because the journal table and the habit_logs table share a `user_id` and a `date`, and Postgres can join them.

Other cross-module queries that fall out for free:

- **Weekend vs weekday spending** — `EXTRACT(DOW FROM date)` over expenses, averaged per day-class.
- **Focus by day-of-week** — Pomodoro minutes grouped by `Date#wday`, surfaces my most productive day.
- **Top categories** — Joined transactions × finance_categories, sorted by sum.
- **Weekly todo throughput** — Completed-vs-created per ISO week.

None of these are clever. They're plain SQL aggregations made possible by the fact that *all the data lives in the same place*. That's the entire point.

## 9. Design Choices Worth Defending

A few decisions I'd defend even though they made the code slightly harder.

**Money as `amount_cents`.** Every monetary value is an integer count of the smallest unit. `money-rails` handles the display. Floats for currency are a class of bug I don't want to debug in production at 11pm.

**Per-account currency.** A transfer between a TRY account and a USD account is not just two opposite-sign rows — it's a transfer with `related_account` and explicit currency on each side. The validation:

```ruby
def transfer_requires_related_account
  return unless kind == "transfer" && related_account_id.blank?
  errors.add(:related_account_id, "must be present for transfers")
end
```

**Polymorphic tags.** Tags live in their own table with a polymorphic join. The cost is one extra index; the benefit is that a tag like `istanbul-2026` can apply to a flight transaction, a packing-list todo, three calendar events, and the journal entry you wrote on the plane — and the global search finds all of them at once.

**No password reset emails.** This is a single-user local app. Devise's `:recoverable` is enabled because it ships in the default, but the SMTP config is intentionally absent. If you forget your password, you reset it from the Rails console. That's a feature: there is no SaaS provider to phish, no email vector, no "reset link expired" friction.

**Brakeman with documented ignores.** The `pg_dump` and `pg_restore` calls in `BackupService` use `Open3.capture3` with an array of arguments — so the shell never interpolates user input — but Brakeman doesn't know that. Rather than refactor the code to satisfy a false positive, the ignore is documented inline. The principle is *use tools, don't bend the code to please them when you understand the trade-off*.

## 10. What Meridian Is Not

Honest limitations matter more than honest features.

- **Not multi-user, not multi-tenant.** The schema has a `user_id` everywhere because that's good hygiene, but the backup service dumps the entire database. Multi-tenant Meridian would need a different export strategy.
- **Not a sync service.** There is no cross-device sync. If you want Meridian on your laptop and your phone, you either run it on a small VPS behind Tailscale, or you back up + restore between devices. Sync is a hard problem and bolting it on later would compromise the local-first guarantee.
- **Not a productivity religion.** Meridian doesn't push a method — no GTD, no Bullet Journal, no Atomic Habits ladder. The modules are deliberately neutral primitives. Use them however your brain works.
- **Not finished.** v1.0.0 shipped on 2026-05-20. The roadmap includes proper recurring transactions, journal templating, more insight cross-sections, and a mobile-friendlier capture flow. The [CHANGELOG](https://github.com/hamzagedikkaya/meridian/blob/main/CHANGELOG.md) is the source of truth.

## 11. Getting Started

```bash
git clone https://github.com/hamzagedikkaya/meridian
cd meridian
bundle install
bin/rails db:create db:migrate db:seed
bin/dev
```

Then <http://localhost:3000>. Seed data ships two users:

- `admin@meridian.local` / `password123` — empty
- `demo@meridian.local` / `demo12345` — populated with 97 transactions, 5 subscriptions, 10 todos, 6 habits with 360 logs, 8 events, 6 journal entries, 4 goals

The demo account is the fastest way to see whether the design works for you before committing your own data to it.
