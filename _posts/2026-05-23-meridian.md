For the last few years, the parts of my life I actually wanted to track had drifted into six different apps. One for money. One for habits. Another for todos. A separate calendar. A journal app that, of course, lived in yet another silo. Each one a small monthly fee. Each one an export format that didn't talk to anyone else. Each one a quiet promise that *your data is yours* — disproved the moment you tried to leave.

[Meridian](https://github.com/hamzagedikkaya/meridian) is what I built to stop renting my own life. It's a single Rails 8 application — finance, habits, todos, calendar, journal, goals, insights — that runs on a machine I control, dumps its entire state into one `tar.gz` when I want a backup, and never phones home. No accounts on someone else's server. No premium tier. No sync that mysteriously breaks the week before tax season.

This post is about the design of that app: what's in it, why local-first instead of hosted, the technical decisions that made it pleasant to live in, what changed after v1.0, and the things I deliberately left out.

> *Updated September 2026.* Since v1.0.0 shipped in May, Meridian gained monthly budgets with pace tracking, an interactive spending breakdown, multi-currency accounts including gram-gold, a full Turkish/English UI, a JSON API, and a Flutter companion app that talks to your server over your own Wi-Fi. Sections 3, 5, 9 and 10 are new or substantially rewritten, and the screenshots are current.

## 1. The Problem with Renting Your Own Data

The honest framing isn't "subscriptions are bad." Some of them are excellent products built by people I respect. The problem is structural: each one captures a thin slice of your life, and the slices never connect.

Your finance app knows you spent ₺840 on coffee in March. Your habit app knows your "no caffeine" streak broke on the 14th. Your journal app — if you keep one — knows you wrote *"didn't sleep well, anxious about the demo"* that same morning. Each fact lives in someone else's database. The obvious question — *do my caffeine relapses line up with my anxious days?* — is unanswerable, because no single system has both facts.

It gets worse when you leave. CSV exports drop fields. APIs get rate-limited. A pricing change can ransom three years of journal entries behind a tier you never signed up for. You don't own the data; you rent access to it.

The local-first answer is the obvious one: **put everything in one Postgres database on a machine you own.** That's the entire thesis. The rest is execution.

## 2. What Meridian Actually Is

Meridian is a single Rails 8 application — not a microservice mesh, not an Electron wrapper, not a "platform." One repo, one database, one process tree, one backup file.

![Meridian dashboard — dark theme, seeded demo account](/assets/images/posts/meridian_dashboard.png)

The dashboard is a bento grid: this month's net with a sparkline, active streaks with a per-habit bar, open todos, today's events, then habits, upcoming todos, the last seven days of spend, and goal progress. It isn't designed to impress in a screenshot. It's designed to be the first thing I see in the morning and the last thing I close at night.

The whole stack:

| Layer | Choice |
|---|---|
| Backend | Ruby 3.3 · Rails 8.1 |
| Frontend | Hotwire (Turbo + Stimulus) · Importmap · Tailwind v4 |
| UI components | ViewComponent + Lookbook |
| Database | PostgreSQL 14+ |
| Background / cache / websockets | Solid Queue · Solid Cache · Solid Cable — all on Postgres |
| Auth | Devise for the browser · bearer tokens for the API |
| Charts | Apache ECharts (finance) · Chartkick + Chart.js · groupdate |
| Money | money-rails · multi-currency incl. a custom gram-gold currency |
| Recurring rules | ice_cube |
| Localization | Turkish · English, per user |
| Backup | `pg_dump` + `tar.gz` + ActiveStorage |
| Testing | RSpec · FactoryBot · Shoulda · Capybara · SimpleCov |
| Quality | RuboCop omakase · Brakeman · Bullet · EagerEye |

The mantra was *fewer moving parts, fewer footguns*. No Node build server — Tailwind runs from its native binary. No Redis — the Solid suite handles jobs, cache and ActionCable on Postgres. No fonts pulled from a CDN at runtime. The app boots, serves traffic, and stays alive on a small box without babysitting.

## 3. One App, Eight Modules

Every module has its own controller surface and view tree, but they share one Postgres database, one `User`, and one polymorphic `Tag`/`Tagging` pair — so a tag like `istanbul-2026` can sit on a flight transaction, a packing-list todo, three calendar events and a journal entry at the same time.

- **Finance** — Accounts with per-account currency, **nested categories with roll-up**, transactions (income / expense / transfer), subscriptions on recurring rules, **monthly budgets with pace tracking**, an interactive spending-breakdown pie with preset and custom date ranges, per-account filter and click-to-drill-down, a six-month trend, CSV export.
- **Todos** — Lists, priorities, statuses, due dates, and filter tabs (Open / Today / This week / Overdue / Done).
- **Habits** — Daily, weekly and monthly cadences, streaks, a 12-week heatmap, completion rate, and a "perfect day" chain. (Streak math in §8.)
- **Calendar** — Monthly grid plus a drag-to-reschedule weekly view, with an iCal feed at `/calendar/feed` so the same events show up in Apple Calendar or Fantastical.
- **Journal** — ActionText rich body, mood emoji, energy level, gratitude, tags, timeline view.
- **Goals** — Financial, habit-linked and custom targets. Progress is recalculated from live data, never stored as a number that drifts; deadlines get colour-coded badges.
- **Insights** — Cross-module analytics. The reason a single database exists (§9).
- **Weekly review** — A guided form that surfaces last week's stats next to three reflection prompts.

![Meridian finance — month net, spending breakdown, categories, accounts and budgets on one page](/assets/images/posts/meridian_finance.png)

Bolted onto all of it:

- **Global search** (`⌘K` / `Ctrl+K` / `/`) — one modal, seven models, arrow-key navigation.
- **Quick capture** (`c`) — one text input, smart router (§6).
- **Focus timer** — a Pomodoro Stimulus controller with browser notifications and per-todo time tracking.
- **Light / dark** — system, dark or light, persisted per user. Dark-first amber palette by default.
- **Bilingual** — every screen in Turkish and English, switchable from Settings; the choice follows the account to the mobile app and back.
- **Vim-style nav** — `g d`, `g f`, `g t`, `g h`, `g c`, `g j`, `g g` for the major sections.

## 4. The Technical Bones

Choosing Rails 8 wasn't nostalgia. Rails 8 ships the *Solid* suite — Solid Queue for jobs, Solid Cache for caching, Solid Cable for ActionCable — all backed by Postgres. That's three subsystems I'd otherwise have needed Redis for, gone. The self-hoster's deployment story collapses to *Postgres + the Rails process*.

The frontend is Hotwire, following a rule I believe in more with every project: **render HTML on the server, swap fragments on the client, write Stimulus controllers only for the genuinely interactive bits.** The Pomodoro timer is a Stimulus controller. The drag-to-reschedule week view is a Stimulus controller. The ECharts finance dashboard is a Stimulus controller that receives its data as a JSON attribute and never fetches anything itself. Everything else is Turbo Frames and Turbo Streams.

ViewComponent + Lookbook handles the UI primitives. Lookbook is mounted at `/lookbook` in development only, so I can preview a `Card`, `Button`, `StatNumber` or chart component in isolation without real data. It's a quiet productivity multiplier.

Design tokens live in one file, `app/assets/tailwind/application.css`, declared inside `@theme` for dark mode with `html.light` overrides. Fraunces (variable serif) for display, DM Sans for body, JetBrains Mono for code. Warm near-black surfaces, cream text, and a single disciplined gold — because every other self-hosted app on the planet defaults to blue.

## 5. Money: Integer Cents, Many Currencies, and a Gram of Gold

Every monetary value in Meridian is an integer count of the currency's smallest unit — `amount_cents`, `monthly_limit_cents`, `balance_cents` — with `money-rails` handling display. Floats for currency are a class of bug I refuse to debug at 11pm.

Each account carries its own currency, and a transfer between a TRY account and a USD account is not two opposite-sign rows: it's one transfer with a `related_account` and an explicit currency on each side. The validation is one method:

```ruby
def transfer_requires_related_account
  return unless kind == "transfer" && related_account_id.blank?
  errors.add(:related_account_id, "must be present for transfers")
end
```

### Gold is a currency

In Türkiye, savings often live in physical gold, and I wanted a savings account that reads `28 gr`, not `₺62,300`. So gram-gold is registered as a real `Money::Currency`:

```ruby
# config/initializers/money.rb
Money::Currency.register(
  iso_code:        "GAU",
  name:            "Gram Altın",
  symbol:          "gr",
  subunit_to_unit: 1,          # no cents — a gram is the unit
  symbol_first:    false
)
```

`subunit_to_unit: 1` is the important line. Everything that formats or parses money — the web views, the CSV export, the quick-capture parser, the API, the mobile app — asks the currency for its subunit instead of assuming 100. That's why `412 gr` never becomes `4,12` on the phone.

### Budgets with a pace tick

A budget is a monthly cap on a root expense category, so subcategory spend rolls up against one number. The status object does the arithmetic once:

```ruby
def pace_percent    = (day_of_month.to_f / days_in_month * 100).round
def projected_cents = (spent_cents.to_f / day_of_month * days_in_month).round
def will_overspend? = !over? && projected_cents > limit_cents
```

The bar shows how much you've used; a vertical tick shows where you *should* be today; and if the projection says you'll cross the cap before month-end, the row says so in words — "Will overspend" — before it happens rather than after.

## 6. Quick Capture: One Input, Smart Router

The most-used feature in the app is one I almost didn't ship. A floating button (and the `c` key) opens a single text field. Whatever you type gets routed to the right module. Since the mobile app arrived, the routing lives in a service object shared by the web controller and the API:

```ruby
# app/services/quick_capture.rb
class QuickCapture
  def call
    return result(:empty) if @text.blank?

    case @text
    when /^[+\-]?\d+(\.\d+)?/                        # "120 coffee" · "+5000 salary"
      capture_transaction
    when /^habit:\s*(.+)/i                           # "habit: reading"
      capture_habit($1.strip)
    when /(?:yarın|tomorrow|salı|monday|tuesday|…)/i # looks like a date → propose an event
      result(:event_suggestion)
    else                                             # everything else is a todo
      result(:todo, record: @user.todos.create!(title: @text, priority: "medium", status: "pending"))
    end
  end

  private

  def capture_transaction
    account = @user.accounts.active.first
    return result(:no_account) if account.nil?

    kind    = @text.start_with?("+") ? "income" : "expense"
    subunit = Money::Currency.find(account.currency)&.subunit_to_unit || 100
    amount  = (@text.delete("^0-9.\-").to_f.abs * subunit).round
    description = @text.sub(/^[+\-]?[\d.]+\s*/, "")

    result(:transaction, record: ::Transaction.create!(
      user: @user, account: account, amount_cents: amount, kind: kind,
      description: description.presence || I18n.t("quick_capture.button"), date: Date.current
    ))
  end
end
```

Four regex arms. No NLP, no model, no "AI assistant." It covers roughly 95% of what I want to capture in two seconds without breaking flow.

`120 coffee` becomes an expense. `+5000 salary` becomes income. `habit: reading` ticks today's log. `Call dentist tuesday` opens a pre-filled event form. `Reply to Mehmet about the demo` becomes a todo. Note the `subunit` line: the same input on a gram-gold account records `2` grams, not `200` — the currency rules from §5 apply here too.

The capture cost is *one keypress plus one sentence*, which is the threshold where a system stops being something I should use and becomes something I just use.

## 7. Backups as a First-Class Feature

If your data lives on one machine, backups aren't a feature — they're the premise. Meridian's backup format is deliberately boring:

```
meridian-backup-YYYYMMDD-HHMMSS/
├── metadata.json   ← Meridian version, schema version, timestamp, user
├── db.dump         ← pg_dump --format=custom
└── storage/        ← the ActiveStorage blob tree (avatars, attachments)
```

That tree is tarred and gzipped into one file. You can `scp` it, drop it on a USB stick, throw it in iCloud Drive. One file is a complete snapshot of *your Meridian*.

Restore is the inverse: upload the archive at `/backups`, the app extracts it, runs `pg_restore --clean --if-exists`, swaps the ActiveStorage tree, and signs you out so you can sign back in with the restored credentials. There's one important guard:

```ruby
meta = JSON.parse(File.read(File.join(workdir, "metadata.json")))
if meta["schema_version"] && meta["schema_version"] != schema_version
  raise "Schema version mismatch: backup is #{meta['schema_version']} but DB is #{schema_version}"
end
```

The destination must be on the same migration version as the backup. That trades a little convenience for safety: you can't accidentally restore a pre-migration dump into a post-migration schema. Upgrade the destination first, then restore.

The whole thing is [`BackupService`](https://github.com/hamzagedikkaya/meridian/blob/main/app/services/backup_service.rb) — about 145 lines including error handling. No external service, no cloud sync. Just `pg_dump`, `tar` and a metadata file.

## 8. Habits, Streaks, and Avoiding the N+1 Trap

The habits module looks innocent. Each habit has many `HabitLog` rows, one per day. A streak for one habit is easy: pull completed dates descending, walk down until you hit a gap.

The trap is the dashboard, which renders *every* active habit with its streak. A naïve `@habits.each(&:current_streak)` costs one query per habit — twelve habits, twelve queries, before the heatmap even renders. The fix is a batched calculator:

```ruby
def self.streaks_for(habits)
  habit_ids = habits.map(&:id)
  return {} if habit_ids.empty?

  today = Date.current
  rows = HabitLog.where(habit_id: habit_ids, completed: true, date: ..today)
                 .order(date: :desc).pluck(:habit_id, :date)
  by_habit = rows.group_by(&:first).transform_values { |arr| arr.map(&:last) }

  habit_ids.index_with do |hid|
    dates = by_habit[hid] || []
    cutoff = dates.include?(today) ? today : today - 1.day
    relevant = dates.drop_while { |d| d > cutoff }
    next 0 if relevant.empty? || relevant.first != cutoff

    streak = 1
    relevant.each_cons(2) { |a, b| (a - b).to_i == 1 ? streak += 1 : break }
    streak
  end
end
```

One query, regardless of how many habits you have. The "perfect day" chain — a day is perfect when every habit active that day was completed — follows the same discipline: two queries for a 30-day window, whatever the habit count.

This is the kind of decision that doesn't matter on day one and matters every day after. It's also precisely the kind of N+1 that runtime tools like Bullet miss, because the loop is inside a custom method rather than a direct association call. I wrote about that class of bug in [Beyond N+1]({% post_url 2025-12-06-beyond_n+1 %}) and built [EagerEye]({% post_url 2026-05-03-eager_eye_static_analysis %}) to catch it statically. Both are in Meridian's Gemfile.

## 9. Insights: The Reason to Have It All in One Database

This is where the local-first thesis pays off. Because finance, habits, journal, todos and focus sessions share one Postgres database, the insights page can ask questions no single SaaS app can:

```ruby
# Mood × habit completion, last 30 days
entries = current_user.journal_entries.where(date: from..to).where.not(mood: nil)
entries.each do |entry|
  logs = current_user.habit_logs.where(date: entry.date)
  by_mood[entry.mood][:count]          += 1
  by_mood[entry.mood][:completed_days] += logs.where(completed: true).count
  by_mood[entry.mood][:total_days]     += logs.count
end
```

Paired with a chart, that answers *"on the days I wrote that I was anxious, what was my habit completion rate?"* — not because a recommendation engine guessed, but because `journal_entries` and `habit_logs` share a `user_id` and a `date`. (Yes, that's two small queries per journal entry. It's bounded by the 30-day window and I've kept it readable rather than clever; at most sixty index lookups is a price I'll pay on a page I open once a week.)

Other cross-module queries that fall out for free:

- **Weekend vs weekday spending** — `EXTRACT(DOW FROM date)` over expenses, averaged per day class.
- **Focus by day of week** — Pomodoro minutes grouped by weekday; surfaces my most productive day.
- **Top categories** — transactions joined to categories, summed, sorted.
- **Weekly todo throughput** — completed vs created per ISO week.

None of it is clever. It's plain SQL aggregation made possible by the fact that *all the data lives in the same place*. That's the whole point.

## 10. The API and Meridian Mobile

The original post said Meridian was "not a sync service" and suggested running it on a VPS if you wanted it on your phone. That answer was unsatisfying, and the fix turned out not to be sync at all: **the phone talks to the same server over your own Wi-Fi.** One database, no cloud tenant, no third party.

### A JSON API under `/api/v1`

The API controllers inherit from `ActionController::API` and authenticate with the user's `api_token` as a bearer token — Devise for the browser, tokens for the phone, one `User` table:

```ruby
def authenticate_api_user!
  @current_user = User.find_by(api_token: bearer_token) if bearer_token.present?
  return if @current_user

  render json: { error: "unauthorized" }, status: :unauthorized
end

def bearer_token = request.authorization.to_s[/\ABearer (.+)\z/, 1]
```

```bash
curl -s http://localhost:3000/api/v1/health                       # unauthenticated ping
curl -s -X POST http://localhost:3000/api/v1/session \
     -d 'email=demo@meridian.local&password=demo12345'            # → {token, user}
curl -s http://localhost:3000/api/v1/home -H "Authorization: Bearer $TOKEN"
```

| Endpoint | Feeds |
|---|---|
| `GET /home` | the entire Today screen in one round trip |
| `GET /finance/dashboard` · `GET /accounts` | net, six-month series, category pie, budgets, subscriptions |
| `GET/POST/PATCH/DELETE /transactions` | the transaction feed with filters and paging |
| `GET /habits` · `PATCH /habits/:id/toggle_today` | habit cards and optimistic toggles |
| `GET /goals` · `PATCH /goals/:id/update_progress` | goal rings and per-type actions |
| `GET/POST/PATCH/DELETE /journal_entries` | journal list, `body_html`, editor |
| `GET /todos` · `PATCH /todos/:id/toggle` · `GET /events` | today's card |
| `POST /quick_captures` | the same router as §6 |
| `PATCH /me` | language and theme chosen on the phone, stored on the account |

The money rule from §5 crosses the wire intact: every amount is an integer `*_cents` accompanied by the currency's `subunit_to_unit`. The phone never divides by 100.

A few behaviours I'm particularly happy with:

- **Optimistic writes.** Checking a todo or ticking a habit updates the UI instantly, then reconciles with the server; a failure rolls back with a snackbar.
- **Offline honesty.** A failed refresh keeps the last good data on screen under a hairline banner — *Offline · last updated 12:40* — instead of a spinner or a blank error page.
- **Bilingual to the number.** `%82` in Turkish, `82%` in English; `1.234,56 ₺` vs `1,234.56 ₺`. The language is stored on the device *and* pushed to the account via `PATCH /me`, so the web app follows.
- **Compile-time localization.** Strings are an abstract Dart class with one member each; a string translated in only one language doesn't compile. No runtime fallback silently hiding a gap.
- **Golden tests in both languages.** Every screen is rendered at phone metrics in Turkish and English, with translated fixtures, as a visual review harness rather than a pass/fail gate.

The mobile app deserves its own post — the money formatting alone is a story — but the headline is that it took exactly zero changes to the local-first guarantee. Your data is still in one Postgres database on your machine. Your phone is just another window into it.

## 11. Design Choices Worth Defending

A few decisions I'd defend even though they made the code slightly harder.

**Money as integer subunits, everywhere.** Covered in §5, but it's the single rule that made multi-currency, gram-gold, quick capture and the API all agree with each other. One function formats money on the web; one function formats it on the phone.

**Polymorphic tags.** Tags live in their own table with a polymorphic join. The cost is one extra index; the benefit is that global search finds a transaction, a todo, three events and a journal entry from one tag in one query.

**Two auth paths, one user table.** Devise sessions for the browser, bearer tokens for the API. No OAuth server, no JWT library, no refresh-token dance — a single `api_token` column and a one-line check.

**No password reset emails.** It's a single-user, local app. Devise's `:recoverable` stays on because it ships in the default, but SMTP is intentionally absent. Forgot your password? Reset it from the Rails console. That's a feature: no SaaS provider to phish, no email vector, no "reset link expired."

**Brakeman with documented ignores.** The `pg_dump` and `pg_restore` calls use `Open3.capture3` with an argument array — the shell never sees user input — but Brakeman can't know that. Rather than contort the code to please a false positive, the ignore is documented inline. Use tools; don't bend the code to satisfy them once you understand the trade-off.

**Readable over clever in cold paths.** The insights loop in §9 is a bounded N+1 on purpose. The habit streak calculator in §8 is batched on purpose. The difference is how often each page renders and how many rows it touches. Optimize the dashboard; leave the weekly report honest and simple.

## 12. What Meridian Is Not

Honest limitations matter more than honest features.

- **Not multi-user, not multi-tenant.** Every table has a `user_id` because that's good hygiene, but the backup service dumps the *entire* database. A multi-tenant Meridian would need per-user export, and that's not on the roadmap.
- **Not a sync service.** There is still exactly one database. The phone reads and writes it over your LAN; it doesn't keep a replica. Cold-start the app with the server unreachable and you get an empty state, not stale data.
- **Not a productivity religion.** No GTD, no Bullet Journal, no Atomic Habits ladder. The modules are neutral primitives. Use them however your brain works.
- **Not finished.** v1.0.0 shipped on 2026-05-20; budgets, the ECharts breakdown, multi-currency, the bilingual UI, the API and the mobile client all landed after it. Still to come: account management from the phone, standalone todo and agenda screens on mobile, journal templates, and more insight cross-sections. The [repository](https://github.com/hamzagedikkaya/meridian) is the source of truth.

## 13. Getting Started

**Requirements:** Ruby 3.3, PostgreSQL 14+, and Node.js 22+ (used only for the native Tailwind binary).

```bash
git clone https://github.com/hamzagedikkaya/meridian
cd meridian
bundle install
bin/rails db:create db:migrate db:seed
bin/dev
```

Then open <http://localhost:3000>. The seed creates two users:

- `admin@meridian.local` / `password123` — empty
- `demo@meridian.local` / `demo12345` — populated with transactions, subscriptions, budgets, todos, habits with months of logs, events, journal entries and goals

The demo account is the fastest way to see whether the design works for you before committing your own data to it.

For the phone, clone [meridian-mobile](https://github.com/hamzagedikkaya/meridian-mobile), run `flutter pub get && flutter run`, and point the login screen at your machine's LAN address — `http://192.168.1.20:3000` or whatever yours is. The credentials fields stay dimmed until the health ping succeeds, so a wrong address can never look like a wrong password.
